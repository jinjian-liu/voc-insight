> 文档版本：V0.3  
> 产品阶段：MVP 初版设计  
> 文档状态：MVP 范围已确认，可进入原型与开发设计

## 1. 文档目的

本文档用于统一产品、设计、前端、后端与算法人员对首版产品的理解，并作为原型设计、技术方案、开发排期、测试验收的基础。

首版重点不是建设完整的 CRM 或工单平台，而是验证以下核心价值：

> 能否把分散、非结构化的客户反馈，自动转化为结构化、可合并、可处理、可追踪的问题，并形成从反馈收集到问题解决的数据闭环。

---

## 2. 项目背景

企业的客户反馈通常分散在客服聊天、邮件、访谈记录、表格及内部群聊中，存在以下问题：

- 信息来源分散，难以统一沉淀和检索；
- 人工阅读、分类和摘要耗时，处理标准不一致；
- 同一问题被多次记录，无法准确判断影响范围；
- 反馈与内部处理任务脱节，问题状态难以追踪；
- 管理人员只能看到反馈数量，难以识别高影响问题及处理瓶颈。

本产品通过 NLP / LLM 将原始反馈转化为结构化分析结果，并进一步归并为可管理的标准问题，实现“反馈收集—问题识别—问题处理—数据复盘”的完整闭环。

## 3. 产品定位与目标

### 3.1 产品定位

面向单一企业售后团队和产品团队的轻量级客户反馈分析与问题管理工具。系统内统一将使用者称为“管理员”。

### 3.2 目标用户

首批用户为售后团队和产品团队，系统不区分普通用户、超级管理员或其他权限角色，统一称为“管理员”。管理员可以录入反馈、确认 AI 结果、处理问题、修改或删除数据、维护问题分类以及查看数据看板。

MVP 不设计登录、账号、密码、成员管理或身份认证。系统默认运行在企业内部可信环境中，所有访问者拥有相同功能权限。

### 3.3 MVP 产品目标

- 降低反馈整理、摘要和分类的人工成本；
- 建立“原始反馈”和“标准问题”的关联关系；
- 识别重复或相似反馈，呈现问题影响范围；
- 让问题可以被处理、跟踪并形成完整操作记录；
- 通过数据看板帮助管理者发现高风险问题和处理瓶颈。

### 3.4 暂不纳入首版

- 替代完整 CRM、在线客服或专业研发项目管理系统；
- 微信、邮件、客服平台等渠道的实时自动同步；
- 图片 OCR 和附件内容理解；
- 完全自动的问题合并与无人工审核的自动流转；
- 复杂权限、跨组织和多租户；
- 登录、账号、密码、成员和身份认证；
- 客户档案、客户名称、联系人、客户等级等客户信息管理；
- 站内、邮件、企业微信等消息通知；
- 自定义报表、预测分析和自动周报。

## 4. 核心概念与数据关系

### 4.1 核心概念

**反馈（Feedback）**：匿名化的原始反馈内容，是事实记录；系统不保存客户名称、联系人、客户编号或客户等级。

**问题（Issue）**：从一条或多条反馈中识别出的、可被内部人员处理的标准事项。

**AI 分析结果（Analysis）**：针对反馈生成的摘要、分类、关键词、严重程度等结构化信息。

**处理记录（Activity）**：问题从创建到解决过程中发生的处理、状态变化和内容修改等操作记录。

### 4.2 数据关系

```text
原始反馈 1 ── 1 AI 分析结果
原始反馈 N ── N 标准问题
标准问题 1 ── N 处理记录
已处理问题 N ── 1 处理者
```

设计原则：反馈与问题必须分开管理。一条反馈可能包含多个问题，多条反馈也可能指向同一个问题。

## 5. 核心业务流程

### 5.1 主流程

```text
录入/导入反馈
    ↓
数据清洗与格式校验
    ↓
AI 结构化分析
    ↓
人工确认分析结果
    ↓
关联已有问题 / 创建新问题
    ↓
确认优先级并进入待处理列表
    ↓
管理员填写处理结果 → 自动更新为已处理并记录处理者
    ↓
看板统计与复盘
```

### 5.2 问题状态

- **待确认**：AI 已生成结果，等待管理员确认是否创建或关联问题；
- **待处理**：问题已确认，尚未填写处理结果；该状态不关联负责人；
- **已处理**：管理员已提交处理结果；系统自动记录处理者和处理时间；
- **无需处理**：经判断不需要进一步处理；
- **重复问题**：该问题记录已合并至另一个主问题。

建议状态流转：

```text
待确认 → 待处理 → 已处理
   └──────────→ 无需处理
              → 重复问题
```

## 6. 功能需求

## 6.1 工作台

### 功能目标

让用户进入系统后快速了解当前工作量和需要立即处理的事项。

### 页面内容

- 指标卡：反馈总数、待确认反馈、待处理问题、高严重度待处理问题、已处理问题；
- 待处理列表：按优先级、严重程度和反馈量排序；
- 风险提醒：高严重度问题、近期反馈快速增长的问题；
- 最新动态：最近的问题创建、处理、状态变化和删除记录。

### 验收标准

- 指标可按统一统计口径正确展示；
- 点击指标可跳转至对应筛选结果；
- 所有管理员查看相同的企业级数据范围。

## 6.2 反馈数据管理

### 6.2.1 单条文本录入

必填字段：

- 反馈原文；
- 反馈时间，默认当前时间；
- 来源渠道。

选填字段：

- 产品或业务模块；
- 外部记录编号；
- 录入备注。

系统不得要求录入或保存客户名称、客户编号、联系人、客户等级等客户信息。若反馈原文中包含此类信息，MVP 不单独解析为客户字段。

录入后，系统保存原文并创建 AI 分析任务。

### 6.2.2 表格批量导入

- MVP 支持 `.xlsx`、`.csv`；
- 用户上传文件后进行字段映射；
- 单个上传文件不得超过 10 MB；
- 提供导入模板下载；
- 导入前预览前若干条数据；
- 对空内容、超长内容、错误日期等数据给出提示；
- 导入完成后展示成功数、失败数及失败原因；
- 导入文件仅用于当次解析，解析完成或失败后立即删除，不提供附件下载或历史文件留存；
- 同一外部记录编号重复导入时进行提示。

### 6.2.3 反馈列表与详情

列表字段：反馈编号、摘要、来源、分类、严重程度、关联问题、分析状态、反馈时间、创建人。

支持按关键词、时间、来源、分类、严重程度、分析状态筛选。

详情页展示：

- 原始反馈及来源信息；
- AI 结构化分析结果；
- 人工修改后的最终结果；
- 相似问题建议；
- 已关联问题；
- 创建及修改记录。

## 6.3 AI 智能分析

### 6.3.1 分析能力

系统调用 DeepSeek API，对反馈执行：

- 问题摘要；
- 一级、二级问题分类；
- 关键词提取；
- 情绪倾向识别；
- 严重程度判断；
- 客户影响描述；
- 建议优先级；
- 缺失信息提示；
- 相似问题候选检索。

### 6.3.2 结构化输出

```json
{
  "summary": "升级后无法导出 Excel",
  "category": "功能异常",
  "subcategory": "数据导出",
  "keywords": ["Excel", "导出失败", "版本升级"],
  "sentiment": "negative",
  "severity": "high",
  "user_impact": "相关团队无法完成日常对账",
  "suggested_priority": "P1",
  "confidence": 0.86,
  "information_missing": ["产品版本", "错误提示", "浏览器环境"]
}
```

### 6.3.3 AI 结果约束

- 问题分类从管理员维护的分类体系中选择；
- 无法判断时标记为“其他/待确认”，不得随意生成大量新分类；
- 严重程度由 AI 建议，用户可以修改；
- AI 不得自动完成问题合并、问题关闭等高影响操作；
- 页面应展示 AI 分析状态：待分析、分析中、成功、失败；
- 分析失败时允许手动重试；
- 保存 AI 原始结果、最终确认结果及修改记录，用于效果评估。

### 6.3.4 预设问题分类

MVP 预设以下六类，管理员可以新增、重命名或删除分类：

1. **功能异常**：已有功能报错、失效或结果不符合预期；
2. **性能与稳定性**：响应慢、卡顿、崩溃、服务不可用；
3. **易用性与交互**：流程复杂、提示不清、界面操作困难；
4. **数据与内容**：数据错误、缺失、不同步或展示异常；
5. **账号与权限**：登录、账号、角色、权限及访问问题；
6. **产品需求**：新增功能、能力增强或业务场景建议。

无法归类的反馈暂记为“其他/待确认”。“其他/待确认”是系统保留分类，不计入六个业务分类。

### 6.3.5 严重程度定义

- **低**：轻微体验问题，有替代方案，不影响主要任务；
- **中**：部分功能受限，影响单个或少量用户完成任务；
- **高**：核心功能不可用或重要数据异常，影响主要业务流程；
- **紧急**：大面积服务中断、重大数据或安全风险，需要立即响应。

### 6.3.6 优先级定义

- **P0**：立即处理；重大服务、安全或数据风险；
- **P1**：高优先级；严重影响核心业务；
- **P2**：正常优先级；影响明确但存在替代方案；
- **P3**：低优先级；体验优化或低频问题。

严重程度描述客观影响，优先级描述企业处理顺序。建议优先级由严重程度、同类反馈频次和时间敏感度共同决定。管理员可以修改或删除反馈、问题及其严重程度和优先级；删除操作必须二次确认并写入审计记录。

## 6.4 相似问题识别

### MVP 方案

- 对新反馈生成文本向量并检索相似的未关闭问题；
- 返回相似度最高的 3～5 个候选；
- 展示问题标题、状态、严重程度、关联反馈数及相似原因摘要；
- 用户选择“关联已有问题”或“创建新问题”；
- 关联后，问题的关联反馈数和最近反馈时间自动更新。

### 业务规则

- 相似度仅用于候选召回，不直接代表同一问题；
- 同一反馈可以关联多个问题，但需由用户明确确认；
- 合并问题时必须保留原问题记录和关联关系；
- 已处理问题再次收到同类反馈时，提示管理员判断是否重新进入待处理状态。

## 6.5 问题全生命周期管理

### 6.5.1 问题列表

列表字段：问题编号、标题、分类、状态、严重程度、优先级、处理者、反馈数、创建时间、更新时间、处理时间。

支持关键词搜索，并按状态、处理者、分类、严重程度、优先级、时间筛选和排序。未处理问题的处理者字段为空。

### 6.5.2 创建问题

创建方式：

- 从反馈确认页创建；
- 在问题模块手动创建；
- 将相似反馈关联至已有问题。

问题字段：

- 标题；
- 问题描述；
- 分类；
- 严重程度；
- 优先级；
- 状态；
- 关联反馈；
- 处理备注。

### 6.5.3 问题详情

- 基础信息；
- 影响概览：关联反馈数、首次/最近反馈时间；
- 关联反馈列表；
- 处理者和处理时间（仅已处理问题展示）；
- 处理记录；
- 解决方案；
- 状态变更时间线。

### 6.5.4 操作要求

- 待处理问题不设置负责人或协作人；
- 管理员点击“完成处理”时必须填写处理结果；提交成功后系统自动将状态更新为“已处理”，并记录当前管理员和处理时间；
- 管理员可以修改或删除反馈、问题、严重程度、优先级及处理结果；删除前必须二次确认；
- 所有关键字段变更均生成操作记录；
- MVP 不设置计划完成时间和逾期规则。

## 6.6 数据分析看板

### MVP 指标

- 反馈总数；
- 新增反馈趋势；
- 待确认反馈数；
- 待处理问题数；
- 高严重度待处理问题数；
- 已处理问题数；
- 问题分类分布；
- 问题状态分布；
- 反馈量最多的问题 Top 10；
- 关联反馈数最多的问题 Top 10；
- 平均首次响应时间；
- 平均解决时间。

### 筛选维度

- 时间范围；
- 来源渠道；
- 问题分类；
- 严重程度；
- 处理者。

### 统计口径

- 反馈总数：符合筛选条件的有效反馈记录数；
- 待处理问题：状态为“待处理”的问题数；
- 首次处理时间：问题创建至管理员首次提交处理结果的时间；
- 解决时间：问题创建至首次进入“已处理”状态的时间。

## 7. 角色与权限

MVP 仅设“管理员”一种概念角色，不设置登录、账号、普通成员、超级管理员或分级数据权限。任何能够访问系统的人均拥有相同的管理员能力：

- 新增、导入、查看、修改和删除反馈；
- 确认和修改 AI 分析结果；
- 创建、处理、修改和删除问题；
- 修改严重程度、优先级及处理结果；
- 查看全部问题、数据看板和操作记录；
- 维护问题分类和来源渠道；
- 在系统入口为当前运行会话填写 DeepSeek API Key。

### 7.1 当前操作人署名

由于系统需要在已处理问题和操作记录中展示处理者，但不设计账号体系，因此采用“操作人署名”方案：

- 首次打开系统时填写“当前操作人名称”，与 DeepSeek API Key 一同完成初始化；
- 操作人名称仅用于处理者和审计记录展示，不用于登录、鉴权或权限控制；
- 名称保存在当前浏览器本地，可在页面顶部随时修改；
- 提交问题处理结果、修改或删除数据时，记录当时的操作人名称；
- 系统不校验名称真实性，也不保证名称唯一；
- 入口页面应明确提示：本系统无身份认证，仅适合部署在可信内部网络。

## 10. 非功能需求

### 性能

- 常规列表和详情页面在正常网络下 2 秒内完成主要内容加载；
- 单个上传文件不得超过 10 MB，单次最多导入 2,000 条反馈；
- AI 分析采用异步任务，不阻塞数据导入；
- 大批量任务展示进度和成功/失败数量。
- 同时最多执行 3 个 AI 请求，单次请求超时 60 秒；失败后自动重试最多 2 次。

### 可靠性

- AI 调用失败支持自动重试和人工重试；
- 批量导入失败不得导致已成功数据回滚或重复写入；
- 关键状态变更及字段修改保留审计日志。
- 上传文件优先在内存中解析，不落盘；无论解析成功或失败，均在请求结束时释放文件内容。

### 安全与隐私

- 系统不提供登录或访问控制，必须部署在企业内网、VPN 或其他可信访问边界内，不建议直接暴露到公网；
- 系统初始化页要求管理员填写当前操作人名称和 DeepSeek API Key，并通过安全连接传递 Key 给后端；
- 前端获得随机会话标识，API Key 仅保存在后端内存并与该会话标识关联，不写入数据库、文件、浏览器持久化存储、日志或分析平台；
- 服务端使用该 Key 调用 DeepSeek API，前端不得在初次提交后再次读取完整 Key；
- API Key 会话空闲 8 小时后自动过期；用户可点击“清除 API Key”；系统正常关闭时清空全部内存 Key；服务重启或异常退出后不得恢复旧 Key；
- 日志和错误信息必须对 API Key 进行屏蔽；
- 对手机号、邮箱等个人信息预留脱敏机制；
- 记录模型调用时间、模型、结果状态，不在普通日志中输出完整敏感原文；
- 后续面向真实企业部署前，需要补充数据保存期限、删除机制和租户隔离方案。

### 可维护性

- AI Prompt 和模型参数应支持版本管理；
- 分类字典可配置；
- 业务规则与模型判断解耦；
- 所有枚举字段统一由后端定义。
- MVP 使用 SQLite 单文件数据库，定期复制数据库文件即可完成备份；
- MVP 采用单体应用和进程内任务队列，不引入 Redis、消息队列、微服务或独立向量数据库。

## 11. AI 效果评估

## 12. MVP 验收场景

### 场景一：单条反馈分析

管理员在初始化页填写操作人名称和当前会话 API Key 后录入一条反馈，系统成功保存原文、异步完成 AI 分析，并允许管理员修改和确认结果。整个过程不要求登录。

### 场景二：批量导入

用户上传标准表格、完成字段映射后，系统展示导入结果；有效数据进入反馈列表，错误数据可定位原因。

### 场景三：关联已有问题

系统对新反馈推荐相似问题；管理员选择一个已有问题后，双方建立关联，问题的关联反馈数正确更新。

### 场景四：创建并处理问题

管理员从反馈创建问题，问题进入待处理状态且不关联负责人；任一管理员填写处理结果后，系统自动更新为已处理并记录处理者、处理时间和完整时间线。

### 场景五：管理看板

管理员通过时间、分类和处理者筛选看板，查看待处理问题、高严重度问题、反馈趋势和平均解决时间，并可跳转至明细列表。

## 14. 建议技术架构（非约束）

```text
Web 前端
  ├─ 反馈/问题管理
  └─ ECharts 数据看板
        ↓ REST API
应用服务
  ├─ 管理员会话
  ├─ 反馈与问题服务
  ├─ 导入任务
  └─ 统计服务
        ↓
AI 服务
  ├─ Prompt 与结构化输出校验
  ├─ DeepSeek API
  ├─ 关键词召回 / LLM 相似度复核
  └─ 重试、日志与效果记录
        ↓
数据层
  └─ SQLite
```

实现建议：前端构建为静态资源，由同一个后端应用提供 REST API；业务数据使用 SQLite；AI 调用和批量任务由进程内异步队列处理。首版不拆分微服务，不引入 Redis、Celery、独立文件服务或向量数据库。

### 14.1 相似问题轻量实现

1. 根据分类、关键词和标题，从未删除的问题中召回最多 20 条候选；
2. 使用 DeepSeek 对候选进行同一问题判断和排序；
3. 向管理员展示相似度最高的 3～5 条；
4. 最终关联或创建新问题由管理员确认。

该方案不依赖额外 Embedding 模型和向量数据库。数据量或检索延迟明显增加后，再评估引入向量检索。

### 14.2 删除策略

- 反馈和问题采用逻辑删除，写入 `deleted_at` 和操作人名称；
- 删除后的记录默认不出现在列表、搜索、统计和相似问题候选中；
- 删除问题前必须解除或重新确认其关联反馈，避免反馈无提示丢失关联；
- MVP 不开发回收站页面，误删恢复可由维护人员直接操作 SQLite 处理；
- 操作日志不允许通过页面删除。

## 15. 已确认的产品约束

1. 首批用户为售后团队和产品团队，统一称为管理员；
2. MVP 仅面向单一企业，不做多租户；
3. 不建立或保存任何客户档案和客户字段；
4. 问题分类支持管理员自定义，并预设六个业务分类；
5. 待处理问题不关联负责人，完成处理时记录处理者；
6. 不提供站内、邮件或企业微信通知；
7. 不设超级管理员，管理员可以修改或删除业务数据；
8. 管理员提交处理结果后，系统自动将问题更新为已处理；
9. 上传文件不超过 10 MB，仅用于导入解析且不保存；
10. DeepSeek API Key 由管理员在入口填写，仅用于后端当前会话，不持久化，并在会话或系统结束时清除。
11. 系统不设计登录和账号体系，仅部署于可信内部访问环境；
12. 使用可修改的“当前操作人名称”记录处理者，不作为身份认证。

## 16. 轻量化技术决策

1. **身份**：无登录、无账号、无鉴权；使用浏览器保存的操作人名称进行署名；
2. **部署**：单体应用，仅部署在可信内网或受控访问环境；
3. **数据库**：SQLite 单文件数据库；
4. **API Key**：后端内存会话保存，空闲 8 小时过期，重启即失效；
5. **文件导入**：最大 10 MB、2,000 条，在内存中解析，不保存原文件；
6. **AI 任务**：进程内异步队列，并发 3、超时 60 秒、最多重试 2 次；
7. **相似问题**：分类与关键词召回，再使用 DeepSeek 复核，不使用独立向量数据库；
8. **删除**：业务数据逻辑删除，操作日志保留；
9. **备份**：通过定期复制 SQLite 数据库文件完成，不建设独立备份服务；
10. **扩展原则**：仅在真实使用量证明有必要时，再引入账号权限、外部队列、向量数据库或多租户架构。

## 17. 成功判断

MVP 上线试用后，可用以下结果判断是否值得继续投入：

- 大部分反馈能够在较少人工修改的情况下完成结构化；
- 用户能够通过相似问题推荐发现并合并重复反馈；
- 每个高影响问题都能追溯至相关原始反馈；
- 管理员可以明确了解问题当前状态、处理者及处理时长；
- 相比原有表格或人工整理流程，反馈进入可处理状态的时间明显缩短。
